# 오전 학습 노트

  ## 1) 크롤링 시스템 구조에서 배운 점

  - 새 기능을 넣기 전에 먼저 **전체 파이프라인**을 봐야 한다는 점을 배웠다.
    (`수집 대상 사이트` → `리스트 파싱` → `상세 URL 추출` → `중복 검사` → `저장`)

  - 단순히 새 크롤러를 추가하는 것보다, 기존 구조의 전제(중복 검사, 저장 규칙, 스케줄 타이밍)가 먼저 맞는지 확인해야
  함을 배웠다.

  ---

  ## 2) 페이지네이션에서 배운 점 (0-based vs 1-based)

  - `페이지 인덱스 기준`이 다르면 데이터가 빠지거나 중복 수집될 수 있다는 걸 실제로 확인했다.
  - 특히 목록 페이지/프론트 코드/백엔드 API가 서로 다른 기준을 쓰는 경우가 흔하다.
  - 결과적으로 **서비스 전반에서 인덱스 규칙을 하나로 통일**해야 안정적인 수집이 가능하다.

  ---

  ## 3) 스케줄 중복 실행에서 배운 점

  - 크롤링은 네트워크/파싱 지연 때문에 실행 시간이 길어질 수 있어, 스케줄이 촘촘하면 겹침이 생길 수 있다.
  - 동기 실행 구조에서는 특히 `처리시간 > 스케줄 간격`일 때 중복 수집, 락 경합, 과부하 가능성이 커진다.
  - 실무에서는 단순히 “동시에 안 돌게”만이 아니라, **실행 중복을 명시적으로 제어**해야 운영 안정성이 올라간다.

  ---

  ## 4) API 키/외부 의존성에서 배운 점

  - 외부 API 키가 잘못되면 “조용한 실패”가 발생해도 로그 상 구분이 어려울 수 있다.
  - `fail-fast`(시작 시 점검)는 장애를 조기에 탐지하고 운영자가 원인 인지 시간을 줄인다.
  - 즉, 외부 의존성은 정상 동작 가정이 아니라 **검증 가능한 전제 조건**으로 다뤄야 한다.
