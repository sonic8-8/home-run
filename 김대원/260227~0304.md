# 0304 학습 : 원시값 포장(Value Object) 정복하기

##  오늘 배운 핵심 개념

오늘은 **원시값 포장(Value Object)** 패턴에 대해 깊이 있게 학습했다. 단순히 코드를 동작시키는 것을 넘어, 어떻게 하면 더 객체지향적이고 안전한 코드를 만들 수 있을지 고민하는 시간이었다.

### 1. 왜 원시값을 포장해야 하는가?

그동안 자동차의 이름은 `String`, 위치는 `int`로만 관리했다. 하지만 `String`이나 `int`는 도메인의 제약 사항(예: 이름은 5자 이하)을 스스로 지킬 수 없다. 이를 객체로 감싸면 **"데이터 스스로가 자신의 유효성을 검증"**하게 되어 코드가 훨씬 견고해진다는 것을 깨달았다.

### 2. VO(Value Object)의 필수 조건

* **불변성(Immutable):** 생성 후 값이 바뀌지 않도록 `final`이나 `readonly`를 사용한다.
* **유효성 검증(Validation):** 생성자에서 잘못된 값이 들어오지 못하도록 '입구 컷'을 한다.
* **동등성(Equality):** 주소값이 달라도 내부 값이 같으면 같은 객체로 인정해준다 (`equals` 재정의).

## 🛠️ 오늘 실천한 코드 변화

* **이전:** `Car` 클래스 내부에서 이름 길이를 체크하고 예외를 던짐 (로직의 비대화).
* **이후:** `CarName`과 `Position`이라는 전담 비서(VO)를 만들어 검증 로직을 분리함. `Car`는 이제 포장된 객체를 믿고 쓰기만 하면 된다.

##  느낀 점 & 깨달은 점

* "원시 타입은 너무 많은 것을 허용한다"는 문장이 가장 기억에 남는다. `String` 타입에 자동차 이름 대신 소설 한 권 분량의 텍스트가 들어가도 타입 시스템은 막지 못한다. 하지만 `CarName` 객체는 이를 단호하게 거절할 수 있다.
* 처음에는 클래스가 많아져서 번거롭다고 생각했지만, 규칙이 바뀌었을 때(예: 이름 5자 -> 10자) 해당 클래스 한 곳만 수정하면 된다는 점이 유지보수 측면에서 엄청난 이점이라는 것을 알게 되었다.

### 1. 단일 책임 원칙(SRP) 적용 및 구조 개선
"하나의 클래스는 하나의 이유로만 변경되어야 한다"는 원칙에 따라 코드의 응집도를 높이고 결합도를 낮추는 작업을 진행했습니다.

* **Service Layer 분리**: Controller에 혼재되어 있던 비즈니스 로직을 `AdminService`, `AuthService` 등 전용 서비스로 위임하여 역할을 명확히 했습니다.
* **God Method 분해**: `ProfileService.updateProfile()` 내부의 거대한 로직을 기능 단위로 쪼개어 7개의 **private helper 메서드**로 재구성했습니다.
* **Domain Entity 독립화**: `Profile` 내부에 존재하던 `EducationItem`, `ExperienceItem` 및 `Project` 내부의 `TechStack` 클래스를 독립 파일로 추출하여 도메인 모델의 가시성을 높였습니다.
* **Frontend Refactoring**: 984줄에 달하던 `AdminProfile.tsx` 컴포넌트를 `useAdminProfile` **커스텀 훅**과 5개의 **서브 컴포넌트**로 분해하여 유지보수성을 확보했습니다.


### 2. 글로벌 예외 처리 및 DTO 검증 체계 구축
사용자 경험과 시스템 안정성을 위해 에러 응답 규격을 통일하고 입력값 검증을 강화했습니다.

* **Global Exception Handling**: `@RestControllerAdvice`를 도입하여 `GlobalExceptionHandler`를 생성했습니다. 이제 400, 404, 500 에러가 일정한 JSON 포맷으로 응답됩니다.
* **Custom Exception**: 기존의 `RuntimeException` 대신 도메인에 특화된 `ResourceNotFoundException` 등을 도입하여 예외의 의미를 명확히 했습니다.
* **Bean Validation**: `spring-boot-starter-validation`을 활용해 DTO 레벨에서 `@Valid`, `@NotBlank`, `@Email` 등의 어노테이션으로 선언적 검증을 적용했습니다.

### 3. 테스트 자동화 및 검증
코드 변경에 대한 신뢰도를 높이기 위해 계층별 테스트 코드를 작성했습니다.

* **Backend Unit Test**: `LocalFileService`, `JwtTokenProvider`, `ViewCountService`, `ProjectService`, `ContactService`에 대한 단위 테스트를 완료했습니다.
* **Integration Test**: `SecurityConfigIntegrationTest`를 통해 Public/Admin 엔드포인트에 대한 권한 제어(12개 케이스)를 검증했습니다.
* **Frontend Test**: Vitest와 `@testing-library/react` 환경을 설정하고 API 모듈에 대한 테스트를 수행했습니다.

### 4. 개발 생산성 및 환경 개선
* **Swagger/OpenAPI**: `springdoc-openapi`를 설정하여 `/swagger-ui/index.html`에서 API 문서를 자동으로 확인할 수 있게 했습니다.
* **CI/CD**: GitHub Actions 워크플로를 구축하여 Backend(Maven)와 Frontend(Vite)의 빌드 및 테스트를 자동화했습니다.

## 배운 점

> **SRP의 실전 적용**
> 단순히 이론으로만 알던 "하나의 이유로만 변경되어야 한다"는 원칙을 Controller-Service 분리, God Method 분해, 커스텀 훅 추출 등의 패턴으로 직접 적용해보며 코드의 가독성과 유지보수성이 비약적으로 상승하는 것을 경험했습니다.

> **효율적인 예외 관리**
> `@RestControllerAdvice`를 활용하면 각 컨트롤러마다 반복되는 `try-catch`를 제거하고 예외를 한 곳에서 일괄 처리할 수 있어 비즈니스 로직에만 집중할 수 있다는 점을 체득했습니다.

> **선언적 검증의 편리함**
> `Bean Validation`을 통해 복잡한 `if`문 없이 어노테이션만으로 데이터 무결성을 보장할 수 있는 효율적인 방법을 익혔습니다. (단, `spring-boot-starter-validation` 의존성 확인 필수)
