# 📌 TDD & 객체지향 & SOLID 학습 정리

------------------------------------------------------------------------

# 1️⃣ TDD 핵심 이해

## 🔴 Red

-   실패하는 테스트를 먼저 작성한다.
-   존재하지 않는 클래스/메서드는 스켈레톤을 생성한 후 테스트를
    실행한다.
-   컴파일 에러는 Red가 아니다.
-   테스트가 FAIL 상태가 되어야 Red이다.

## 🟢 Green

-   테스트를 통과하는 최소 코드만 작성한다.
-   처음부터 완벽한 구조를 만들지 않는다.

## 🔵 Refactor

-   테스트가 통과된 상태에서 구조를 개선한다.
-   책임을 분리하고, 중복을 제거하며, 필요한 추상화를 도입한다.

TDD는 단순한 테스트 작성 기법이 아니라 설계를 개선하는 도구이다.

------------------------------------------------------------------------

# 2️⃣ 콘솔 출력 문제에서 배운 설계 원칙

## 기존 문제

-   로직 내부에서 print()를 직접 호출했다.
-   출력까지 테스트하려다 구조가 복잡해졌다.

## 개선 방향

-   Umpire는 판정 계산만 담당한다.
-   Formatter는 결과 문자열 생성만 담당한다.
-   Printer(View)는 출력만 담당한다.

핵심은 도메인 로직과 입출력을 분리하는 것이다. 출력은 비즈니스 로직의
책임이 아니다.

------------------------------------------------------------------------

# 3️⃣ SOLID 원칙 적용 정리

## 🟢 S --- 단일 책임 원칙 (SRP)

-   Umpire는 계산만 담당한다.
-   Printer는 출력만 담당한다.
-   InputHandler는 입력만 담당한다.
-   계산과 출력, 도메인과 IO를 분리한다.

## 🟢 O --- 개방-폐쇄 원칙 (OCP)

-   출력 방식을 Console에서 File이나 Web으로 변경하더라도 기존 Game
    코드를 수정하지 않도록 설계해야 한다.
-   인터페이스를 활용하면 확장에는 열려 있고 수정에는 닫힌 구조를 만들
    수 있다.

## 🟢 L --- 리스코프 치환 원칙 (LSP)

-   InputHandler를 ConsoleInputHandler나 MockInputHandler로 교체해도
    Game은 동일하게 동작해야 한다.
-   하위 타입은 상위 타입을 완전히 대체 가능해야 한다.

## 🟢 I --- 인터페이스 분리 원칙 (ISP)

-   InputHandler는 입력 기능만 제공한다.
-   Printer는 출력 기능만 제공한다.
-   불필요하게 많은 기능을 가진 거대한 인터페이스는 지양한다.

## 🟢 D --- 의존성 역전 원칙 (DIP)

나쁜 구조 예시: - Game이 InputHandler를 직접 생성하여 의존하는 구조

개선 구조: - 생성자 주입을 통해 추상화에 의존하도록 변경

예시:

    public Game(InputHandler inputHandler) {
        this.inputHandler = inputHandler;
    }

-   구체 클래스가 아닌 추상화에 의존한다.
-   테스트가 쉬워진다.
-   결합도가 낮아진다.

------------------------------------------------------------------------

# 4️⃣ 인터페이스 분리에 대한 정리

-   단순 콘솔 게임이라면 인터페이스 분리는 필수가 아니다.
-   테스트에서 Mock 주입이 필요하다면 의미가 있다.
-   입력 방식이 바뀔 가능성이 있다면 도입할 가치가 있다.
-   무조건적인 추상화는 오버엔지니어링이 될 수 있다.
-   변화 가능성을 기준으로 설계해야 한다.

------------------------------------------------------------------------

# 5️⃣ 테스트 가능한 구조의 특징

-   로직과 출력이 분리되어 있다.
-   객체를 직접 new로 생성하지 않고 생성자 주입을 사용한다.
-   구체 클래스가 아닌 인터페이스에 의존한다.
-   테스트 코드에서 대체 구현을 주입할 수 있다.

------------------------------------------------------------------------

# 6️⃣ 가장 큰 학습 포인트

-   TDD는 설계를 강제하는 도구이다.
-   테스트를 먼저 작성하면 자연스럽게 SOLID 원칙이 적용된다.
-   객체지향은 추상화를 많이 하는 것이 아니라 변화에 강한 구조를 만드는
    것이다.
-   모든 인터페이스가 좋은 것은 아니며, 필요할 때 도입해야 한다.
