### 1. Early Return 
Early Return은 조건을 만족하지 않는 경우를 메서드 초반에 바로 반환(return)하는 방식이다. 예외 상황이나 종료 조건을 먼저 처리해서, 핵심 로직이 더 잘 보이게 만드는 기법이다.

- 왜 사용하나? 가장 큰 이유는 코드의 가독성을 높이기 위해서!
    - 예외 조건을 먼저 제거하고, 마지막에 핵심 로직만 남길 수 있다.

- 좋은 활용 방안
    1) 유효성 검증  
입력값이 잘못되었을 때 바로 종료하거나 예외를 던진다.

    2) 예외 상황 먼저 처리  
정상 흐름보다 예외 상황이 적을 때, 예외를 먼저 걸러내는 것이 읽기 쉽다.

- 사용 시 주의할 점
    1) return이 너무 많으면 오히려 흐름이 흩어질 수 있다.  
    메서드가 너무 길고 return이 지나치게 많으면 읽기 불편해질 수 있다.  
    이 경우는 메서드를 더 분리하는 것이 맞다.

    2) 단순히 return만 하지 말고 의도를 분명히 해야 한다.
    왜 종료하는지 드러나야 한다. 필요하면 예외를 던지거나 메서드 이름으로 의미를 보완해야 한다.

    3) 핵심 로직이 단순할 때 더 효과적이다.  
    복잡한 비즈니스 로직 전체를 Early Return만으로 해결하려 하면 오히려 어색할 수 있다.

### 2. 메서드 및 관심사 분리
메서드 분리는 하나의 메서드 안에 여러 일을 몰아넣지 않고, 의미 있는 단위로 나누는 것이다. 관심사 분리는 서로 다른 책임을 분리하는 것이다.

- 왜 사용하나?

    1) 코드의 역할이 명확해진다.  
    한 메서드가 하나의 일만 하면 이름만 봐도 역할을 이해할 수 있다.  
    ex) validateInput(), countStrike()
    이렇게 나누면 각 책임이 분명하다.

    2) 테스트가 쉬워진다.  
    관심사가 섞여 있으면 테스트도 어렵다. 
    예를 들어 계산 로직과 출력 로직이 붙어 있으면 숫자 판정을 테스트하고 싶은데 콘솔 출력까지 같이 다뤄야 한다.  
    반면 분리하면:  
    countStrike()는 계산만 테스트  
    formatResult()는 문자열만 테스트  
    printResult()는 출력만 테스트   

    이렇게 각각 독립적으로 검증할 수 있다.

    3) 수정 범위가 줄어든다.  
    출력 문구를 바꾸고 싶은데 계산 로직까지 건드리면 위험하다.    
    관심사가 분리되어 있으면 필요한 부분만 안전하게 수정할 수 있다.

    4) 재사용성이 높아진다.
    계산 로직과 출력 로직이 분리되어 있으면 콘솔이 아니라 웹, 앱, API 응답에서도 계산 로직을 재사용할 수 있다.

- 좋은 활용 방안
    1) 한 메서드가 한 가지 일만 하게 만들기
    메서드를 읽었을 때 “이 메서드는 무엇을 하는가?”에 한 문장으로 답할 수 있어야 한다.

    2) 계산과 출력을 분리하기
    도메인 로직은 계산만 하고, 출력은 바깥에서 처리하는 것이 좋다.

    3) 검증 로직 따로 분리하기
    검증은 대부분 핵심 계산과 별개의 책임이다.ㅜ따로 빼는 것이 읽기 좋다.

    4) 이름으로 의도를 드러내기
    메서드를 분리했으면 이름이 중요하다.  
    좋은 이름은 내부 구현을 몰라도 역할이 보이게 해준다.

    5) 클래스 단위 관심사 분리까지 연결하기
    메서드 분리를 하다 보면, 아예 클래스를 나누는 것이 더 자연스러운 경우도 있다.

- 사용 시 주의할 점
    1) 무조건 잘게 쪼개는 것이 좋은 것은 아니다
    메서드를 너무 과하게 나누면 오히려 흐름이 끊기고 읽기 어려워질 수 있다.

    2) 분리 기준은 “줄 수”가 아니라 “책임”이다
    짧은 메서드라도 책임이 두세 개 섞여 있으면 분리 대상이다.
    반대로 조금 길어도 하나의 책임만 수행하면 괜찮을 수 있다.

    3) 메서드 이름이 역할을 설명해야 한다
    분리만 해놓고 이름이 모호하면 오히려 더 읽기 어렵다.



## 데일리 컨텐츠 학습 - DB 정규화
- 동일한 의미의 속성을 하나의 테이블로 집약
- **논리적**모델링 단계에서 불필요한 데이터의 중복 속성 제거

### DB 정규화 특징
- 테이블 간 중복 데이터의 최소화
    - 저장 용량 최적화
    - 데이터 무결성 유지

1) 1 정규화
    - 중복 속성 형태 분리
    - 반복 속성 제거
    - 새로운 테이블 추가한 후 기존 테이블과 1:N 관계 형성
    - 유연한 확장성 보장, 스키마 변경 최소화

2) 2 정규화
    - 부분 종속 관게 분리
    - 기본키가 복합키로 구성되었을 때, 복합 키 중 일부에 의존적인 열 제거

3) 3 정규화
    - 기본키에 종속되지 않고, 일반 열에 의존적인 컬럼이 있다면 이를 제거

- 정규화의 단점
    - Join 연산 증가로 인한 Query 응답 시간 증가 => 부분 반정규화 진행


## DB 반 정규화
- 복잡한 쿼리 성능을 최적화하기 위해 테이블간 중복을 허용하는 작업
- 테이블/컬럼/릴레이션 레벨로 중복, 통합, 분리 수행
- 2개 이상의 테이블에 동일 컬럼을 중복 배치하여, 조회 시간을 최적화

1. 특정 범위의 데이터만 자주 처리
- 전체 테이블 검색 대신 해당 범위의 데이터만 빠르게 조회할 수 있도록 하여 데이터를 분리하는게 효율적
- 이는 불필요한 데이터의 로딩을 줄여서 성능을 향상 시킴

2. 요약/집계 정보가 자주 요구되는 경우
- 집계 작업을 수행할 때마다 원시 데이터를 일일이 계산하면 처리 시간 증가, 성능 저하
- 자주 요구되는 요약 정보 미리 저장 -> 불필요한 계산 피하고 빠르게 결과 조회

3. 이력 정보가 필요한 경우
- Entity의 변경 이력을 관리할 때, 변경된 데이터를 추적하기 위해 이력 테이블을 추가
- 이를 통해 과거 데이터를 쉽게 조회하고, 데이터의 변동 사항을 분석할 수 있음

4. Join으로 성능 저하가 예상될 때
- 여러 테이블 간 Join이 많아지면, 쿼리 성능이 크게 저하될 수 있음
- 반 정규화를 통해 Join이 잦은 데이터를 중복 저장하면, 필요 데이터를 바로 조회할 수 있어 성능이 개선될 수 있음


## DB 정규화 vs 반 정규화
- 정규화: 데이터 중복을 최소화하여 무결성 보장 
- 반정규화: 중복을 허용하여 성능을 최적화
