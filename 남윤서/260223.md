# ⚾ TDD 기반 숫자야구 게임 학습 회고록

**날짜:** 2026.02.23 (월)  
**주제:** TDD + 객체지향 설계 원칙 적용 실습

---

## 1. 생성자 기반 의존성 주입 (Dependency Injection)

### 문제

`BaseBall` 클래스 내부에서 직접 객체를 생성하는 구조였다.

```java
InputHandler inputHandler = new ConsoleInputHandler();
OutputHandler outputHandler = new ConsoleOutputHandler();
RandomNumber randomNumber = new RandomNumber();
```

이 구조는 `BaseBall`이 구체 클래스에 강하게 의존하기 때문에 테스트 시 Mock 객체 주입이 불가능하고, 입력 방식 교체가 어렵다.

### 개선

```java
public BaseBall(InputHandler inputHandler,
                OutputHandler outputHandler,
                RandomNumber randomNumber) {
    this.inputHandler = inputHandler;
    this.outputHandler = outputHandler;
    this.randomNumber = randomNumber;
}
```

`Application`에서 구체 객체를 주입하고, 테스트 코드에서는 Fake 객체를 주입할 수 있게 되었다.

### 핵심 포인트

- 상위 모듈(`BaseBall`)은 구체 클래스가 아닌 **인터페이스에 의존**해야 한다. → DIP(의존성 역전 원칙)
- 의존성 주입 구조가 갖춰져야 비로소 **진정한 단위 테스트**가 가능해진다.
- 입력 방식을 파일·웹·GUI로 교체할 때 `BaseBall` 코드를 수정할 필요가 없다.

## 2. 게임 생명주기와 상태 격리

게임을 재시작할 때마다 새로운 `InputHandler` / `OutputHandler` 인스턴스를 사용하도록 설계했다.

하나의 객체를 재사용해도 될 것 같지만, TDD 관점에서는 **테스트 케이스 하나 = 독립된 환경 하나**여야 한다. 인스턴스를 분리하지 않으면 이전 게임의 상태가 남아 다음 테스트에 영향을 줄 수 있다.

> 상태 공유는 버그의 씨앗이다. 객체는 가능한 한 불변에 가깝게 유지하라.

## 3. 문자열 비교 오류 수정 (`==` → `.equals()`)

### 문제

```java
if (restartNum == ("1")) { ... }  // 참조값(주소) 비교
```

Java에서 `==`은 객체의 메모리 주소를 비교한다. 사용자 입력으로 생성된 `String`은 리터럴 `"1"`과 다른 주소를 가지기 때문에, 이 비교는 항상 `false`가 될 수 있다.

### 개선

```java
if (restartNum.equals("1")) { ... }  // 값 비교
```

| 비교 방식 | 동작 | 사용 상황 |
|---|---|---|
| `==` | 참조값(메모리 주소) 비교 | 기본 타입(`int`, `char` 등) |
| `.equals()` | 실제 값 비교 | `String` 등 참조 타입 |

## 4. Umpire 클래스 — 매개변수 제거 및 필드 관리

### 문제

```java
// 메서드 호출마다 같은 값을 반복 전달
public int countStrike(String ranNum, String userNum) { ... }
public int countBall(String ranNum, String userNum) { ... }
```

`Umpire`가 비교할 데이터를 소유하지 않고, 매 호출 시 외부에서 전달받는 구조였다. 데이터 없이 메서드만 있는 객체는 응집도가 낮다.

### 개선

```java
public class Umpire {
    private final String ranNum;
    private final String userNum;

    public Umpire(String ranNum, String userNum) {
        this.ranNum = ranNum;
        this.userNum = userNum;
    }

    public int countStrike() { ... }
    public int countBall() { ... }
}

// 호출부가 간결해짐
int strike = umpire.countStrike();
int ball   = umpire.countBall();
```

### 핵심 포인트

`Umpire`는 **"두 숫자를 비교하는 심판"** 이다. 비교 대상은 심판이 생성될 때 이미 확정되어야 하며, 내부 상태로 관리하는 것이 자연스럽다. 객체는 **데이터를 소유하고, 그 데이터를 처리하는 행동을 가져야 한다.**

## 5. 메서드 책임 위임 — `checkStrike(int i)` → `countStrike()`

### 문제

```java
// 외부에서 반복문을 돌려 인덱스를 직접 전달
int strike = 0;
for (int i = 0; i < 3; i++) {
    if (umpire.checkStrike(i)) strike++;
}
```

외부 호출자가 `Umpire` 내부 구조(인덱스)를 알고 있어야 한다. 이는 캡슐화 위반이자 응집도 저하의 원인이다.

### 개선

```java
// Umpire가 전체 계산을 책임짐
int strike = umpire.countStrike();
```

**Tell, Don't Ask** 원칙에 따라 외부에서 데이터를 꺼내 계산하는 대신, 객체에게 일을 시키고 결과만 받는다.

## 🔍 향후 개선 과제

| 항목 | 현재 상태 | 개선 방향 |
|---|---|---|
| 불변 객체 | `Umpire` 필드 변경 가능 | `final` 키워드 적용 |
| 입력 유효성 검증 | 처리 없음 | 길이·숫자·중복을 `Validator` 객체로 분리 |
| 전략 패턴 | `RandomNumber` 구현체 하나 | 인터페이스 분리 후 고정값·랜덤 전략 교체 가능하게 구성 |
| 도메인 객체 | `String` 기반 비교 (Primitive Obsession) | `Number` 값 객체로 추상화 |
| 테스트 코드 | Given-When-Then 구조 미적용 | `@DisplayName` 사용, 구조 통일 |

---

## 📌 핵심 교훈

- TDD는 테스트를 만드는 도구가 아니라, **좋은 설계를 강제하는 도구**다.
- **의존성 주입**은 테스트 가능성을 만들고, **인터페이스**는 유연성을 만든다.
- 객체는 데이터를 소유하고, 그 데이터를 처리하는 행동을 가져야 한다.
- 작동하는 코드와 **설계가 설명되는 코드**는 다르다.
