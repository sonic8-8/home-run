## 🪜 Step 1 — 이름 짓기 & 매직 넘버 (`BadUmpire`)

### Before
```java
public int doS(List<Integer> a, List<Integer> b) {
    int r = 0;
    for (int i = 0; i < 3; i++) {
        if (a.get(i).equals(b.get(i))) {
            r++;
        }
    }
    return r;
}
```

### After
```java
public static final int NUMBER_SIZE = 3;

public int countStrike(List<Integer> ranNum, List<Integer> userNum) {
    int check = 0;
    for (int i = 0; i < NUMBER_SIZE; i++) {
        if (ranNum.get(i).equals(userNum.get(i))) {
            check++;
        }
    }
    return check;
}
```

### 변경 포인트
- `doS` → `countStrike`, `doB` → `countBall` : 메서드가 무슨 일을 하는지 이름만 보면 알 수 있다
- `a`, `b`, `r` → `ranNum`, `userNum`, `check` : 역할을 담은 변수명
- 하드코딩된 `3` → `public static final int NUMBER_SIZE = 3` : 매직 넘버 상수 추출

### 💡 느낀 점
> `doS`와 `doB`는 기능적으로 완벽히 동작하지만, 3개월 뒤의 나는 이게 Strike인지 Score인지 알 수 없다. **이름은 의도를 담는 그릇이다.**

## 🪜 Step 2 — Early Return (`DeepUmpire`)

### Before — depth 3~4단계의 중첩 if-else
```java
public int countStrike(List<Integer> answer, List<Integer> guess) {
    int strikeCount = 0;
    if (answer != null && guess != null) {
        if (answer.size() == TARGET_SIZE && guess.size() == TARGET_SIZE) {
            for (int index = 0; index < TARGET_SIZE; index++) {
                if (answer.get(index).equals(guess.get(index))) {
                    strikeCount++;
                } else {
                    // TODO: 이 else 블록은 어떤 가치를 제공하고 있나요?
                }
            }
        } else {
            throw new IllegalArgumentException("입력값의 길이가 올바르지 않습니다.");
        }
    } else {
        throw new IllegalArgumentException("입력값은 null일 수 없습니다.");
    }
    return strikeCount;
}
```

### After — Early Return으로 평탄화
```java
public int countStrike(List<Integer> answer, List<Integer> guess) {
    if (answer == null || guess == null) {
        throw new IllegalArgumentException("입력값은 null일 수 없습니다.");
    }
    if (answer.size() != TARGET_SIZE || guess.size() != TARGET_SIZE) {
        throw new IllegalArgumentException("입력값의 길이가 올바르지 않습니다.");
    }
    int strikeCount = 0;
    for (int index = 0; index < TARGET_SIZE; index++) {
        if (answer.get(index).equals(guess.get(index))) {
            strikeCount++;
        }
    }
    return strikeCount;
}
```

### 변경 포인트
- null 체크, 길이 체크를 **먼저 throw**해서 조기 종료 → 이후 로직은 flat하게 작성
- 의미 없는 빈 `else` 블록 완전 제거
- 최대 들여쓰기 depth: **4단계 → 1단계**
- 두 번째 조건문의 `==` 버그도 `!=` 로 함께 수정

### 💡 느낀 점
> `else`를 지우면 코드가 망가질 것 같았는데, 오히려 더 읽기 쉬워졌다. **예외 케이스를 먼저 쳐내면 핵심 로직이 드러난다.**

## 🪜 Step 3 — 메서드 분리 (`MassiveUmpire`)

### Before — 모든 로직이 `playGame()` 하나에
```java
public int[] playGame(List<String> rawAnswer, List<String> rawGuess) {
    // 1. 입력 검증 (10줄)
    // 2. 파싱 (10줄)
    // 3. 스트라이크 판정 (7줄)
    // 4. 볼 판정 (9줄)
    // 5. 결과 반환
}
```

### After — `playGame()`이 목차처럼 읽힌다
```java
public int[] playGame(List<String> rawAnswer, List<String> rawGuess) {
    validateInput(rawAnswer, rawGuess);
    int[] answer = parseInput(rawAnswer);
    int[] guess  = parseInput(rawGuess);
    int strike   = countStrike(answer, guess);
    int ball     = countBall(answer, guess);
    return new int[] { strike, ball };
}
```

### 추출한 Private 메서드

| 메서드 | 역할 |
|--------|------|
| `validateInput()` | null 체크, 길이 체크 |
| `parseInput()` | `List<String>` → `int[]` 변환, 숫자 아닐 경우 예외 처리 |
| `countStrike()` | 같은 위치 같은 숫자 카운트 |
| `countBall()` | 다른 위치 같은 숫자 카운트 |

### 💡 느낀 점
> 리팩토링 후 `playGame()` 6줄을 읽으면 전체 흐름이 한눈에 들어온다. **메서드 이름이 주석을 대신한다.**  
> `parseInput()`을 answer와 guess 양쪽에 재사용할 수 있게 된 것도 분리의 덤이었다.

## 🪜 Step 4 — 관심사 분리 (`ConsoleUmpire`)

### Before — 도메인 로직과 출력이 강하게 결합

```java
        System.out.println("낫싱");

```

### After — 인터페이스와 구현체로 IO 분리

```
📁 구조
├── InputHandler             (interface)  입력 추상화
├── OutputHandler            (interface)  출력 추상화
├── ConsoleInputHandler      (구현체)     System.in 사용
└── ConsoleOutputHandler     (구현체)     System.out 사용

ConsoleUmpire → OutputHandler를 주입받아 사용
                System.out 직접 의존 완전 제거
```

### 이렇게 되면 뭐가 좋아지나?

- **테스트 가능:** `OutputHandler` Mock 구현체를 주입해서 출력 문구를 단위 테스트로 검증 가능
- **이식성:** 웹/모바일로 바꿀 때 `ConsoleOutputHandler` → `WebOutputHandler` 교체만 하면 됨
- **도메인 순수성:** `ConsoleUmpire` 내부에 `System.out` 한 줄도 남지 않음

### 달성한 테스트
```
✅ 1스트라이크일 때 → "1스트라이크"
✅ 3스트라이크일 때 → "3스트라이크" + "게임 종료" 메시지
✅ 낫싱(0볼 0스트라이크) → "낫싱"
✅ 1볼 1스트라이크일 때 → "1볼 1스트라이크"
```

### 💡 느낀 점
> `System.out.println` 한 줄이 테스트를 막고, 이식을 막고, 설계를 망친다.  
> **테스트하기 어려운 코드는 설계가 잘못된 신호다.** 인터페이스로 분리하고 나니 테스트가 자연스럽게 따라왔다.
