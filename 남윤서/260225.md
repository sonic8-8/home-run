# 🚗 2026-02-25 회고

> **주제:** Car / Cars 설계 개선 + IO 분리 + 검증 흐름 정리  
> **핵심 키워드:** `일급 컬렉션` `책임 분리` `응집도` `변경 가능성`

---

## 1️⃣ Car 객체와 Cars 일급 컬렉션

### 🔎 문제
- 자동차 여러 대를 `List<Car>`로 직접 다루면서 이름 길이, 중복 검증, 출력 포맷 등의 규칙이 호출부에 흩어질 위험이 있었다.
- Car 관련 로직이 여러 파일에 분산되면 규칙 변경 시 수정 범위가 넓어질 수 있다.

### ✅ 개선
- `Car`는 자신의 상태와 단일 책임(이름, 전진 행동)만 관리하도록 설계했다.
- `Cars`를 일급 컬렉션으로 도입해 집합 행동과 컬렉션 규칙을 한 곳에 모았다.
- 내부 컬렉션을 캡슐화하여 외부에서 직접 접근하지 못하도록 제한했다.

### 🎯 핵심 포인트

> 일급 컬렉션은 데이터와 규칙을 함께 묶는다.  
> 컬렉션 직접 접근을 줄이면 변경 지점이 줄어든다.

| 객체 | 책임 |
|------|------|
| `Car` | 자신의 상태와 행동만 책임진다 |
| `Cars` | 여러 Car를 관리하고 집합 로직을 책임진다 |

---

## 2️⃣ IO 로직 분리

### 🔎 문제
- 입력 파싱과 출력 포맷이 도메인 로직과 섞이면 테스트가 어려워진다.
- 출력 형식 변경이 도메인 코드 수정으로 이어질 수 있다.

### ✅ 개선
- `Input` / `Output` 전용 클래스를 분리했다.
- 도메인 객체는 입력과 출력의 형태를 전혀 모르게 설계했다.
- 의존 방향을 단순화했다.

```
Application → IO → Domain
```

### 🎯 핵심 포인트

> 변경 가능성이 높은 영역을 경계 밖으로 밀어내는 것이 유지보수에 유리하다.

| 영역 | 역할 |
|------|------|
| `Domain` | 순수 비즈니스 로직 |
| `IO` | 외부 세계와의 연결 지점 |

---

## 3️⃣ 입력 검증 규칙 통합

### 🔎 문제
- 자동차 이름 길이 제한, 빈 값 처리, 중복 여부 등의 검증이 여러 위치에 흩어질 위험이 있었다.
- 검증 로직이 분산되면 에러 메시지의 일관성이 깨질 수 있다.

### ✅ 개선
- 검증 포인트를 한 곳으로 통합했다.
- 유효하지 않은 입력은 즉시 예외 처리했다. (**Fail Fast**)
- 규칙 변경 시 수정 지점을 최소화했다.

### 🎯 핵심 포인트

> **"검증은 한 곳에서"** 가 핵심이다.  
> 도메인으로 넘기기 전에 입력을 선처리한다. 규칙은 흩어지지 않도록 고정시켜야 한다.

---

## 4️⃣ 도메인 관점의 데이터 흐름 정리

### 🔎 문제
- 문자열 기반 처리 위주로 흐르면 도메인의 의미가 흐려진다.
- 호출부가 상태를 조립하면 도메인 객체가 수동적이 된다.

### ✅ 개선
- 도메인 객체가 스스로 의미 있는 상태를 가지도록 설계했다.
- 실행 흐름은 `Application`에서 조립하고, 실제 로직은 도메인이 담당하도록 분리했다.

### 🎯 핵심 포인트

> 객체는 데이터를 소유하고, 그 데이터를 처리하는 행동을 함께 가진다.  
> 호출부는 **"조립"** 만 하고, 로직은 **도메인** 이 맡는다.

## 🛠 향후 개선 과제

| 항목 | 현재 상태 | 개선 방향 |
|------|-----------|-----------|
| 이름 검증 | 기본 검증만 처리 | Validator 분리, 규칙 확장 (길이/공백/중복) |
| 출력 포맷 | 문자열 조합 중심 | View / Formatter 분리 |
| 입력 파싱 | 문자열 기반 | 값 객체 도입으로 의미 강화 |
| 테스트 구조 | 케이스별 확인 중심 | Given-When-Then 구조 통일 |

## 📌 핵심 교훈

- **일급 컬렉션**은 규칙의 위치를 고정시켜준다.
- **IO 분리**는 테스트 가능성과 유지보수성의 출발점이다.
- 좋은 설계는 **"변경될 것"과 "변경되지 않을 것"을 먼저 분리**하는 데서 시작한다.
