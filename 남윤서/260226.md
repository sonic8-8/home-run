# 🏁 2026-02-26 회고

> **날짜:** 2026.02.26 (목)  
> **주제:** Race 로직 분리 + 랜덤 의존성 격리 + 결과 산출 구조화

---

## 1️⃣ 레이스 진행 로직 분리

### 🔎 문제
- 레이스 진행이 단순 반복문에 흩어지면 테스트가 어려워진다.
- "몇 라운드 진행"과 "각 라운드에서 전진 여부"가 뒤섞이기 쉽다.

### ✅ 개선
- 레이스 진행을 전담하는 로직을 분리해 흐름을 명확히 했다.
- 라운드 단위 진행과 자동차 이동 판단을 분리하여 책임을 좁혔다.

### 🎯 핵심 포인트

> "진행"과 "판단"을 나누면 변경 포인트가 분리된다.  
> 흐름을 도메인에 맡기면 호출부는 단순해진다.

---

## 2️⃣ 랜덤 요소 격리

### 🔎 문제
- 전진 여부가 랜덤에 의존하면 테스트가 비결정적이 된다.
- 랜덤이 도메인 내부에 박혀 있으면 검증이 어렵다.

### ✅ 개선
- 랜덤 값 생성 로직을 분리해 테스트에서 고정값을 주입 가능하게 했다.
- 실행 시에는 실제 랜덤 구현체를 사용하되, 테스트에서는 Fake/Stub으로 교체했다.

### 🎯 핵심 포인트

> 비결정적 요소는 반드시 경계 밖으로 밀어낸다.  
> 의존성 주입이 있어야 레이스 로직 자체를 안정적으로 테스트할 수 있다.

| 환경 | 사용 구현체 |
|------|-------------|
| 실행 시 | 실제 랜덤 구현체 |
| 테스트 시 | Fake / Stub |

---

## 3️⃣ 결과 산출 분리 (우승자 계산)

### 🔎 문제
- 결과 계산이 진행 로직에 섞이면 변경 시 영향 범위가 커진다.
- 출력 형식과 결과 계산이 연결되면 설계가 경직된다.

### ✅ 개선
- 우승자 산출 로직을 별도 단계로 분리해 변경에 유연하도록 구성했다.
- 결과 계산은 도메인 내부에서 처리하고, 출력은 IO에서 맡도록 분리했다.

### 🎯 핵심 포인트

> 계산과 출력은 다른 책임이다.  
> 결과 산출 로직은 재사용 가능한 도메인 규칙으로 고정한다.

| 영역 | 책임 |
|------|------|
| `Domain` | 우승자 결과 계산 |
| `IO` | 결과 출력 |

---

## 4️⃣ 실행 테스트 관점 정리

### 🔎 문제
- 단순 실행 테스트가 "실행이 된다" 수준에 머무르면 회귀를 잡기 어렵다.
- 랜덤이 개입되면 테스트의 기대값을 설정하기 어렵다.

### ✅ 개선
- 고정된 랜덤 값을 주입해 라운드별 이동 결과를 검증할 수 있게 했다.
- 결과 산출까지 포함한 시나리오 테스트를 설계해 흐름 검증을 강화했다.

### 🎯 핵심 포인트

> 테스트는 흐름을 고정하고, 로직을 검증하는 도구다.  
> 랜덤을 격리하면 "정확한 기대값"을 세울 수 있다.

## 🛠 향후 개선 과제

| 항목 | 현재 상태 | 개선 방향 |
|------|-----------|-----------|
| 전진 규칙 | 임계값 고정 | 규칙 전략 분리 (정책 교체 가능) |
| 결과 산출 | 단일 규칙 | 동점 처리 / 공동 우승 규칙 확장 |
| 테스트 구조 | 시나리오 중심 | 파라미터 테스트로 케이스 확장 |
| 출력 정책 | 문자열 조합 | View 레이어 분리 + 포맷 책임 강화 |

---

## 📌 핵심 교훈

- **랜덤과 같은 외부 의존성**은 격리할수록 설계가 단단해진다.
- **레이스 진행, 이동 판단, 결과 산출**을 분리하면 테스트와 변경이 쉬워진다.
- TDD는 **"실행"이 아니라 "설계"를 검증**하는 과정이다.
