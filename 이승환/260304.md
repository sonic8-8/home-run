# 2026년 03월 04일 수요일 학습 회고록

## 1. 🏎️ 불변 객체, Naming, 그리고 파서의 위치

### 📌 배경
자동차 미션의 완성을 향해 달려가며, 불변 객체(Immutable Object)를 제대로 다루는 방법과, 네이밍(Naming)의 미학, 도메인과 UI 사이의 책임 분배에 대한 확고한 기준을 세웠습니다.

### 🔥 미션을 수행하며 마주친 실수와 교훈들

#### 1. 불변 객체의 가장 흔한 실수: "허공에 외침"
**상황:** `Position`의 내부 숫자를 `final`로 만들고 `increase()`를 호출해 전진하게 했는데, 테스트 코드에서 거리는 여전히 0이었습니다.

```java
// ❌ 새 객체를 받았지만 버려짐
public void moveForward() {
    position.increase(); 
}

// ✅ 새로운 상태 통째로 내 손에 다시 쥐기 (재할당)
public void moveForward() {
    this.position = position.next(); 
}
```

**교훈:** 불변 객체는 자신의 상태를 쥐고 흔드는 것이 아니라, 연산의 결과로 "새로운 객체"를 뱉어낸다는 특징을 직접 버그를 고치며 체득했습니다. `String`의 `concat()`과 완전히 같은 원리였습니다.

#### 2. 불변 객체의 네이밍(Naming): `next()`, `consume()`
**상황:** `increase()`라는 함수명이 "내부 값이 변한다"는 오해를 줄 수 있다고 직감했습니다. 수정한 시도 횟수(`TryCount`) 또한 `decrease()`나 `minus(1)`이 도메인 관점에서 어색해 보였습니다.

**교훈:**
- 값 객체(VO)의 메서드는 행위를 당한 과거분사(`moved()`)나 다음 상태(`next()`), 또는 전치사(`plus(1)`)를 사용하여 **본질이 변하지 않음**을 나타내야 합니다.
- `TryCount`의 경우 기계적으로 숫자가 줄어드는 것에 집중하기보다 **"기회를 소진한다(consume)"**는 도메인 중심의 언어를 사용함으로써 코드가 훨씬 유창하고 설명적(Descriptive)으로 변하는 것을 경험했습니다.

#### 3. 기계적 `for`문 부수기 (Value Object의 진면모)
**상황:** `Racing` 컨트롤러 안에 덩그러니 놓인 시도 횟수 지시자 `int count`와 `for(int i=0; i<count; i++)` 로직이 거슬렸습니다.

**교훈:** 단순 횟수를 `TryCount`라는 하나의 객체로 승격시키니, `while(tryCount.isPlayable()) { tryCount = tryCount.consume(); }` 와 같은 우아한 객체 지향 흐름이 탄생했습니다. 단순 원시값을 포장했을 뿐인데 절차지향적 코드가 객체 지향적 책임을 가지게 되는 마법을 겪었습니다.

#### 4. 파서(Parser)의 로직을 VO 안으로 옮긴다면?
**상황:** 문자열을 파싱하는 책임을 `CarName` 같은 VO 팩토리 안에 넣을지 고민했습니다.

**교훈:** **절대 옮겨서는 안 됩니다!** "쉼표(,)로 나눈다"거나 "문자열을 숫자로 바꾼다"는 것은 UI 또는 프레젠테이션 계층의 지식일 뿐, 도메인 비즈니스 규칙이 아님을 깨달았습니다. 파서(Parser)가 바깥에서 더러운 문자열을 순수 데이터로 정제해 도메인에 넘겨주는 것이 레이어드 아키텍처의 아름다운 결합도 분리입니다.
