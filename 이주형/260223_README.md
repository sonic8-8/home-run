## 데이터 모델링 시 주의사항
- 관계가 없는 엔터티는 잘 못 도출된 엔터티
- 속성명 설계 시 유일하게 설계할 것

## 1. TDD 핵심 원칙: Red → Green → Refactor

### 🔴 Red
- 실패하는 테스트를 먼저 작성
- 필요한 클래스/메서드는 IDE로 빈 껍데기 생성
- **컴파일 성공 + 테스트 실패 상태**가 Red
- 기능을 다 만든 뒤 테스트 추가하는 것은 TDD가 아님

### 🟢 Green
- 테스트를 통과시키는 **최소한의 코드** 작성
- “잘 짜는 것”보다 “통과시키는 것”이 우선

### 🔵 Refactor
- 테스트가 통과하는 상태를 유지하며 구조 개선
- 책임 분리, 중복 제거, 가독성 개선
- 리팩토링 후 반드시 테스트 재실행

# 읽기 좋은 코드와 추상화

## 1. 왜 읽기 좋은 코드가 중요한가?

읽기 좋은 코드는 단순히 “보기 좋은 코드”가 아니다.

가독성 ↑  
→ 이해도 ↑  
→ 유지보수 용이  
→ 시간·비용 절감

코드를 이해하지 못하면 수정할 수 없고,  
이해하기 어려운 코드는 수정 과정에서 버그를 만든다.

핵심은 이것이다:

> 동작하는 클린 코드만이 의미가 있다.  
> (Clean code that works)

## 2. 기본 개념 정리

- **도메인**: 해결하려는 문제 영역  
  (예: 주문, 결제, 재고, 키오스크 등)

- **도메인 지식**: 요구사항을 구현하는 과정에서 발견되는 문제 구조에 대한 이해

- **레거시**: 현재 우리가 가지고 있는 기존 코드 전체  
  (나쁜 코드라는 뜻이 아님)

- **조상 / 후손**
    - 조상 = 과거의 개발자
    - 후손 = 미래의 유지보수자

코드는 항상 미래의 누군가가 읽는다는 전제를 가져야 한다.
