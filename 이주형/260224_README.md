# 읽기 좋은 코드와 추상화

## 1. 추상이란?

> 중요한 정보는 남기고, 덜 중요한 정보는 생략하는 것

일상 예시로 지하철 노선도는 실제 거리/곡선을 생략하고,
"어떤 역에서 어떤 역으로 이동 가능한가"라는 핵심만 보여준다.

프로그래밍에서도 동일하다.
`sendEmail(to, subject, body)`는 내부 SMTP 연결, 소켓 통신, 인코딩 같은 구현 세부를 감추고
"이메일을 보낸다"는 목적만 드러내는 추상화다.

컴퓨터 과학 자체가 추상화의 연속이다.
- 1bit -> 자료형 -> 고수준 언어 -> 프레임워크
- 고수준/저수준 언어의 차이 = 추상화 레벨의 차이

## 2. 잘못된 추상화의 원인

1. **중요 정보를 걸러내지 못함**
- 핵심 로직과 부가 처리(로깅, 검증 등)가 한곳에 섞이면 의도가 흐려진다.

2. **공유 문맥(context) 부재**
- 같은 이름도 사람마다 다르게 해석되면 추상화가 실패한다.
- 예: `data`가 API 응답인지 DB 결과인지 불명확한 경우

3. **도메인 불명확**
- 어떤 문제를 푸는 코드인지 불분명하면 이름도 모호해진다.

핵심은 **도메인 안에서 추상화**하는 것이다.
- `Status`보다 `OrderStatus`, `PaymentStatus`처럼 문맥을 드러내기

## 3. 이름 짓기: 가장 단순하지만 중요한 추상화

### 3.1 이름 짓기 4대 원칙

| 원칙 | 설명 | 예시 |
| --- | --- | --- |
| 단수/복수 구분 | 단일 값인지 컬렉션인지 드러내기 | `user`, `users` |
| 이름 줄이지 않기 | 축약어로 의미 손실 방지 | `cnt` -> `count` |
| 은어/방언 지양 | 팀 밖에서도 통하는 보편 용어 사용 | 팀 용어 사전 운영 |
| 좋은 코드에서 학습 | 업계 관용 표현 습득 | `pool`, `candidate`, `threshold` |

### 3.2 실전 팁
- boolean은 `is`, `has`, `can` 접두어 사용 (`isAllOpened`, `hasPermission`)
- `i`, `j` 대신 `row`, `col`처럼 의미 있는 이름 사용
- 협업 시 도메인 용어 사전으로 단어 의미 통일

## 4. 메서드와 추상화

한 문단의 주제가 하나여야 하듯,
한 메서드도 하나의 주제(책임)만 가져야 읽기 쉽다.

- 검증, 계산, 저장, 알림이 한 메서드에 섞이면 이해 비용이 커진다.
- 역할별 메서드로 분리하면 이름 자체가 추상화 계층이 된다.
- 한 줄 코드라도 의미 전달이 좋아지면 추출 가치가 있다.

### 4.1 메서드 선언부와 시그니처
- 선언부: `반환타입 메서드명(파라미터) { 구현부 }`
- 시그니처: `메서드명 + 파라미터 타입/개수/순서`

### 4.2 파라미터 설계
- 파라미터는 외부 세계가 내부 세계에 정보를 전달하는 통로
- 파라미터만 보고도 무엇을 전달해야 하는지 명확해야 함
- 메서드명 + 전치사 조합으로 자연어처럼 읽히게 설계
- 예: `findProductsBy(Category category)`

### 4.3 반환 타입 설계
- 가능하면 `void` 대신 검증 가능한 반환값 고려
- 반환값이 있으면 테스트 단언(`assertEquals`)이 쉬워진다
- `check...` 메서드는 관례적으로 `void` + 실패 시 예외

---

## 5. 추상화 레벨

메서드 추출 시 경계가 생긴다.
- 외부 세계: "무엇을 하는가"(높은 추상화)
- 내부 세계: "어떻게 하는가"(낮은 추상화)

예: `calculateTotalPrice()` 호출부는 목적 중심,
구현부는 `stream().mapToInt().sum()` 같은 세부 중심

### 5.1 핵심 규칙
> 하나의 메서드(하나의 세계) 안에서는 추상화 레벨을 동등하게 맞춘다.

높은 수준의 흐름 속에 갑자기 낮은 수준의 구현이 섞이면,
읽는 사람의 사고 모드 전환이 잦아져 가독성이 급격히 떨어진다.

정리하면:
- 외부는 의도 중심
- 내부는 구현 중심
- 한 블록 안에서는 같은 추상화 높이를 유지
