# TypeScript TDD & 리팩토링 학습 정리

> 숫자 야구 게임 구현을 통해 익힌 TDD 사이클과 리팩토링 원칙

---

## 1. TDD (Test-Driven Development) 기본 사이클

**Red → Green → Refactor**

| 단계 | 설명 |
|------|------|
| 🔴 Red | 실패하는 테스트를 먼저 작성한다 |
| 🟢 Green | 테스트를 통과하는 최소한의 코드를 작성한다 |
| 🔵 Refactor | 기능은 유지하면서 코드를 개선한다 |

> ⚠️ **규칙**: 테스트 코드를 먼저 작성(Red)할 것. 기능부터 짜지 않는다.

## 2. 도메인 객체 설계 — 이름 짓기

### 나쁜 예시
```typescript
export class BadUmpire {
  public doS(a: number[], b: number[]): number { ... }  // 이름이 모호
  public doB(a: number[], b: number[]): number { ... }  // 의도 파악 불가
}
```

### 좋은 예시
```typescript
export class Umpire {
  public judge(answer: number[], guess: number[]): UmpireResult {
    return {
      strikes: this.countStrikes(answer, guess),
      balls: this.countBalls(answer, guess),
    };
  }

  private countStrikes(answer: number[], guess: number[]): number { ... }
  private countBalls(answer: number[], guess: number[]): number { ... }
}
```

**이름 짓기 기준**: "이 코드를 처음 보는 사람이 3초 안에 이해할 수 있는가"

## 3. 관심사 분리 (도메인 ↔ UI 분리)

### 문제: 비즈니스 로직 + 콘솔 출력이 강하게 결합된 코드
```typescript
// ❌ 나쁜 구조
export class ConsoleUmpire {
  public play(answer: number[], guess: number[]): void {
    const strikeCount = this.countStrike(answer, guess);
    const ballCount = this.countBall(answer, guess);
    
    // 판정 로직 안에 console.log가 직접 박혀 있음
    if (strikeCount === 3) {
      console.log("3스트라이크");
      console.log("3개의 숫자를 모두 맞히셨습니다! 게임 종료");
      return;
    }
    // ...
  }
}
```

### 문제점
1. 자동화된 단위 테스트로 출력 결과를 검증하기 극도로 어려움
2. 웹/모바일로 이식 시 코드를 전부 다시 짜야 함

### 해결: 도메인(판정)과 UI(출력)를 분리
```typescript
// ✅ 좋은 구조

// 도메인 — 순수한 판정 로직만
export type UmpireResult = {
  strikes: number;
  balls: number;
};

export class Umpire {
  public judge(answer: number[], guess: number[]): UmpireResult {
    return {
      strikes: this.countStrikes(answer, guess),
      balls: this.countBalls(answer, guess),
    };
  }
}

// UI — 출력 전담
export function printResult(result: UmpireResult): string {
  if (result.strikes === 3) return "3스트라이크\n3개의 숫자를 모두 맞히셨습니다! 게임 종료";
  if (result.strikes === 0 && result.balls === 0) return "낫싱";
  
  const msgs: string[] = [];
  if (result.balls > 0) msgs.push(`${result.balls}볼`);
  if (result.strikes > 0) msgs.push(`${result.strikes}스트라이크`);
  return msgs.join(" ");
}
```

### 분리 후 테스트 작성
```typescript
import { Umpire, printResult } from './umpire';

describe('Umpire', () => {
  const umpire = new Umpire();

  it('1스트라이크', () => {
    const result = umpire.judge([1, 2, 3], [1, 4, 5]);
    expect(result.strikes).toBe(1);
    expect(printResult(result)).toBe("1스트라이크");
  });

  it('낫싱', () => {
    const result = umpire.judge([1, 2, 3], [4, 5, 6]);
    expect(result.strikes).toBe(0);
    expect(printResult(result)).toBe("낫싱");
  });

  it('1볼 1스트라이크', () => {
    const result = umpire.judge([1, 2, 3], [1, 3, 4]);
    expect(result.balls).toBe(1);
    expect(result.strikes).toBe(1);
    expect(printResult(result)).toBe("1볼 1스트라이크");
  });
});
```

> **핵심**: 숫자 검증은 `result.strikes/balls`로, 문자열 검증은 `printResult(result)`로 분리

## 4. 랜덤의 격리 (테스트 불가능한 영역 분리)

### 문제: `Math.random()`이 직접 박혀 있으면 테스트 불가
```typescript
// ❌ 테스트 불가능
function generateRandomNumbers(): number[] {
  const numbers: number[] = [];
  while (numbers.length < 3) {
    const num = Math.floor(Math.random() * 9) + 1;
    if (!numbers.includes(num)) {
      numbers.push(num);
    }
  }
  return numbers;
}
```

### 해결: 인터페이스로 랜덤 생성기를 주입
```typescript
// ✅ 테스트 가능 — 생성기를 외부에서 주입
type NumberGenerator = () => number;

function generateNumber(gen: NumberGenerator): number[] {
  const numbers: number[] = [];
  while (numbers.length < 3) {
    const num = gen();
    if (!numbers.includes(num)) {
      numbers.push(num);
    }
  }
  return numbers;
}

// 테스트에서 가짜 생성기 주입
test('중복 숫자는 스킵하고 3개를 채운다', () => {
  const sequence = [1, 1, 2, 3];
  let idx = 0;
  const gen = () => sequence[idx++];
  
  expect(generateNumber(gen)).toEqual([1, 2, 3]);  // 두 번째 1이 스킵됨을 증명
});
```

## 5. TypeScript `interface` vs `type` 구분

| 기능 | `interface` | `type` |
|------|:-----------:|:------:|
| 객체 구조 정의 | ✅ | ✅ |
| 클래스 `implements` | ✅ | ✅ |
| `extends` 확장 | ✅ | ✅ (`&` 사용) |
| 선언 병합 (Declaration Merging) | ✅ | ❌ |
| 유니온 타입 | ❌ | ✅ |
| 튜플, 원시 타입 별칭 | ❌ | ✅ |
| 조건부/매핑 타입 | ❌ | ✅ |

### 실무 가이드라인
- **객체 구조 → `interface` 우선**
- **유니온, 튜플, 조건부 타입 → `type`**
- 팀 내 일관성이 가장 중요

```typescript
// interface — 객체 구조
interface UmpireResult {
  strikes: number;
  balls: number;
}

// type — 유니온, 단순 데이터 구조
type UmpireResult = {
  strikes: number;
  balls: number;
};
// 이 경우 둘 다 동작하지만, type은 팀 컨벤션 or 유니온 확장 가능성 있을 때 선택
```

## 6. Union vs Enum

### 컴파일 결과 차이 — 핵심 차이

```typescript
// Union → 컴파일 후 흔적 없음 (타입만 존재)
type Direction = 'left' | 'right' | 'up' | 'down';

// Enum → 컴파일 후 실제 JS 객체로 남음
enum Direction {
  Left = 'left',
  Right = 'right',
}
// 컴파일 결과:
// var Direction;
// (function (Direction) { Direction["Left"] = "left"; })(Direction || (Direction = {}));
```

### 숫자 Enum의 함정 — 역방향 매핑
```typescript
enum Status { Active, Inactive }  // 숫자 enum

Status[0]  // 'Active' ← 역방향 매핑 자동 생성 (의도치 않은 동작 주의)
```
> 숫자 enum은 가급적 피하는 것이 좋다.

### 실무 추천: `const` 객체 + Union 조합
```typescript
const Direction = {
  Left: 'left',
  Right: 'right',
  Up: 'up',
  Down: 'down',
} as const;

type Direction = typeof Direction[keyof typeof Direction];
// → 'left' | 'right' | 'up' | 'down'

// 런타임에서도 사용 가능
Object.values(Direction);    // ✅
console.log(Direction.Left); // ✅ 'left'
```

| | Union | Enum | const + Union |
|--|:-----:|:----:|:-------------:|
| 런타임 존재 | ❌ | ✅ | ✅ |
| JS 번들 크기 | 작음 | 커짐 | 작음 |
| 순회 가능 | ❌ | ✅ | ✅ |
| 트리쉐이킹 | ✅ | ❌ | ✅ |

> 단순 타입 구분 → **Union**, 런타임 순회/참조 필요 → **const + Union** 또는 **Enum**

## 7. 핵심 요약

1. **TDD**: 테스트 먼저(Red) → 구현(Green) → 개선(Refactor)
2. **이름 짓기**: 처음 보는 사람이 3초 안에 이해할 수 있는 이름
3. **관심사 분리**: 도메인(순수 로직) ↔ UI(출력) 분리 → 테스트 용이
4. **랜덤 격리**: 제어 불가 영역은 인터페이스로 주입받아 테스트 가능하게
5. **interface vs type**: 객체 구조는 interface, 나머지는 type
6. **Enum**: 숫자 enum 주의, 실무에서는 `const + Union` 선호
